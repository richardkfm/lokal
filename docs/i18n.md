# Internationalization

German is the source language. English is wired from the start so that expanding
beyond Germany is a content problem, not an architecture problem.

## Setup

| File                                   | Role                                                        |
| -------------------------------------- | ----------------------------------------------------------- |
| `src/i18n/routing.ts`                  | Locale list, default locale, `isLocale` guard               |
| `src/i18n/request.ts`                  | Resolves the active locale and loads its catalog            |
| `src/i18n/navigation.ts`               | Locale-aware `Link`, `redirect`, `useRouter`, `usePathname` |
| `src/proxy.ts`                         | Locale negotiation and prefixing                            |
| `messages/de.json`, `messages/en.json` | Message catalogs                                            |

Routes live under `src/app/[locale]/`. `/` redirects to `/de`; an unknown locale
segment returns 404 rather than silently falling back, because a report rendered in
an unexpected language is worse than an error.

Next.js 16 renamed the `middleware` convention to `proxy`. With a `src/` directory
the file must be `src/proxy.ts`, next to `app`.

## Why the engine never returns sentences

The engine emits **rationale codes with parameters**:

```ts
{ code: "rationale.capacity.external_support_likely", params: { category: "helpdesk" } }
```

Renderers translate them. This is the reason the engine can stay pure and the
reason a German report and an English report describe the same plan rather than two
independently written ones.

Rulepack entries are data rather than UI chrome, so they carry localized fields
inline (`{ de, en }`) instead of message keys.

## Locale resolution outside the request

`src/i18n/request.ts` uses `requestLocale`, not `next/root-params`, because it is
also reached from Route Handlers where root params are unavailable. An explicitly
passed locale always wins:

```ts
const t = await getTranslations({ locale: assessment.locale, namespace: "report" });
```

The Markdown export uses that form, and only it. Its route carries no locale
segment, so the language the report was created in is the only signal it has.

**The report view does the opposite, deliberately.** `/[locale]/report/[id]`
takes its locale from `getLocale()` — the request — not from
`assessment.locale`. The stored locale records which language the respondent
answered in, which is worth keeping and is not a statement about who reads the
result. Reading it in the view meant `/en/report/<id>` served German tool
summaries, prerequisite labels and AI descriptions for every report a German
respondent had produced: every string that comes from the rulepack rather than
the catalogue, which is most of the document's substance.

That survived a release because `locale.spec.ts` seeded its fixture with
`locale: "en"`, so the view's stored-locale read and the request agreed and the
bug could not appear. The spec now also posts a German-taken assessment and
reads it at `/en`, which is what any real English reader does the moment they
use the locale switch.

## ICU plurals

Counts go through ICU plural forms — `{count, plural, one {…} other {# …}}` —
rather than a bare `{count}` beside a plural noun.

This is worth a paragraph because of how it was missed. The catalogue avoided
plurals for a whole release, and every report said "1 Bereiche sollten vorerst
unverändert bleiben". Not because anyone decided against them, but because the
tests used a hand-written stand-in for next-intl that substituted `{name}` with
a regular expression and could not evaluate a plural: a message using one would
have failed the suite. A test double that cannot express what the real formatter
can will quietly shape the catalogue to fit the double.

`tests/fixtures/translator.ts` now wraps next-intl's own `createTranslator` with
an `onError` that throws, so the tests format messages exactly as production
does and strictness is a configuration rather than a reimplementation.

## Rules

- Add keys to `messages/de.json` first, then mirror them into `messages/en.json`.
- `tests/i18n/messages.test.ts` fails on any structural drift or empty value. A
  missing key otherwise surfaces as a raw key path inside a document someone is
  about to send to their management.
- English may never lag German in coverage, and does not lag in rendering
  either: `tests/e2e/locale.spec.ts` renders all four surfaces at `/en`, plus a
  German-taken report read at `/en`, and fails on German in the text or in an
  accessible name. Idiomatic polish is the only gap left, and it is a small one.
- Dates reach the reader in the reader's convention, including the price
  observation dates the rulepack stores as ISO. A German report saying "erhoben
  am 2026-08-30" three lines under a header reading "30. August 2026" has two
  date formats on one page, and the ISO one reads as machine output — beside
  the only figures in the document anyone will check against an invoice.
- Accessible names come from the catalogue, never from a literal. The
  `lokal/no-hardcoded-accessible-names` ESLint rule enforces it, because
  `aria-label="Fortschritt"` is invisible to a design pass, a copy pass and axe
  alike — all three missed exactly that.
- Dates and numbers are formatted through next-intl with a fixed `Europe/Berlin`
  time zone, so a report's stated generation date does not shift with server
  location.
